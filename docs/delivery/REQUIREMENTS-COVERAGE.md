# Requirements coverage — measured

For every business requirement in `docs/product/01-requirements-baseline.md`
(G-1…G-19, P-1…P-26, E-1…E-19, plus supplementary O-1…O-7), this document
records what satisfies it now, how a user reaches it, which demonstration record
shows it, and which automated test proves it — with the test's actual result.

This is the **final measurement for release 1.0.0**. It replaces the 2026-09-17
measurement row for row. That one was taken before the final build wave, when
780 tests existed. It was brought up to date on 2026-09-18 with the last round:

- the navigation redesign and global search;
- Admin → Integrations: AI, Doc AI, horizon scanning, e-mail over SMTP or
  Microsoft Graph, and single sign-on;
- the help assistant reading the illustrated guides;
- the four notices moved onto templates.

## 1. Method

**Date measured:** 2026-09-18, against the final working tree (release 1.0.0),
the rebuilt demonstration site `consilium.localhost`, and a clean test site.

**What "satisfies it" means here.** Every claim was checked on disk or in the
database. Older delivery documents were not relied on. Every row was
re-measured, not carried forward.

* **Screens.** Every portal page under `apps/consilium/consilium/www/` was read
  to see which API calls it makes. A page counts as able to *act* only if it
  calls a whitelisted endpoint or a REST write. A page that only reads counts as
  a view.
* **Backend reachability.** Public functions were grepped for callers outside
  tests. A function counts as reachable only if one of these reaches it:
  - a whitelisted endpoint that a page calls,
  - a desk button (`add_custom_button`),
  - a document controller hook (`validate`, `on_update` and so on),
  - a `hooks.py` doc event or scheduled job,
  - the framework's own Workflow engine.

  A function reachable only from tests or from `deploy/demo_data.py` counts as
  **having no screen**.
* **Demonstration data.** Queried read-only from `consilium.localhost` after it
  was rebuilt from scratch: seed plus demo in about 27 s, no failed section,
  idempotent. It holds 14 forums, 15 governing documents, 157 document
  versions, 15 escalation matters, 67 meetings, 24 motions, 137 votes, 92
  attestation tasks, 23 personas and 49 notification templates. Every record
  name below exists in that database; personas are `@demo.example`. **The
  demonstration data was reloaded after the previous measurement, so record
  numbers differ from it.** For example, FRM-2026-00001 is now the Board of
  Directors, and the confidential document is GDOC-00010.
* **Tests.** 1453 test methods were found statically in
  `apps/consilium/consilium/**/test_*.py`, and the run reported `Ran 1453
  tests`, so every test is accounted for. Tests are cited as
  `module.tests.test_file.Class`. "(all N)" means every test in that class,
  counted from the source.

**Test run** (full app suite, `run-tests --app consilium`, on a clean site of
its own, one run, no concurrent runs):

```
Ran 1453 tests in 1432.778s
OK
```

**1453 passed, 0 failed.** This is the final run, after the review pass's
interface fixes: 0 failures, 0 errors. The earlier full runs were `Ran 1372
tests … OK` before the last round, and 1442 during it. The state-name checker
caught one failure in that run, a comparison in the new Integrations code,

### 1.2 Reachability classes

| Class | Meaning |
|---|---|
| **a** | Reachable through a purpose-built portal screen: the CS screens the trace names exist and do their part. Desk is used only where the trace names a DK surface. |
| **b** | Reachable through the desk, configuration or a scheduled job **by design**: the trace names only DK or BG surfaces for the key action. |
| **c** | Partly reachable. The backend exists, but a step has no screen, is desk-only where the trace calls for a custom screen, or is reachable only from code. |
| **d** | Not implemented, **wholly or in a mandatory clause.** The class is the weakest mandatory clause; the "What satisfies it" cell names the missing clause. |

**What moved in the final wave.**

* **Class d → a or b (16 mandatory requirements, plus O-6 and O-7):**
  - G-9, E-12: revert of forums and matters.
  - P-1, P-13, P-19: confidential and restricted handling is enforced on every path.
  - P-6: regulatory-change import and fan-out (also O-7).
  - P-7, P-10, P-11: step service levels, warnings and reminders.
  - P-14: templated, e-mailed notices across the whole lifecycle, approval steps included.
  - P-15: naming.
  - P-24: glossary enforcement.
  - E-7: pathway participants.
  - E-11: quarterly returns and reminders.
  - E-13: time in each status.
  - E-17: templated notices.
  - O-6, O-7: rule-based analysis features, with optional AI commentary.
* **Class c → a (most of the rest):**
  - The policy and escalation portal write paths.
  - The inbox (CS-10) and import review (CS-11).
  - Charter challenge and charter versions (G-7, G-15).
  - Disbandment (G-11).
  - Reporting (P-4, P-12, P-22).
  - Intake (P-16).
  - Disposition (P-26).
  - The forum map and forum escalations tab (O-2, O-5).
* **Re-graded downward on a strict re-reading, with no regression in code:**
  - G-8 (a → d): the approval path cannot vary by forum type or materiality.
  - G-10 (c → d): nothing enforces the first quarter.
  - G-13 (b → c): chairs cannot nominate their own delegate.
  - E-8 (c → d): transitions are not configurable by type and severity.
  - E-9 (d, a different clause now): no configurable approval chain for risk
    acceptance.

### 4.4 Other findings from this measurement

These are verified, but outside any single row.

1. **Every notice now goes through a template.** Two notices used to bypass
   the templates: the approval-step notices on a governing document
   (`policy/routing.py`) and the disbandment approval request
   (`governance/lifecycle.py`, `raise_disbandment`). They were moved to
   `notification.notify` after this measurement was first drawn, with four new
   events: `policy.approval.requested`, `policy.approval.decided`,
   `policy.approval.bypassed` and `governance.disbandment.approval_requested`.
   The events are seeded on migrate and editable per channel. No caller of
   `notify_many` remains outside tests. P-14 moved from (d) to (b). G-14 stays
   in (d) for its meeting and charter-review notices.
2. **A scratch DocType is in the working tree.** `ABC` sits in
   `apps/consilium/consilium/consilium_core/doctype/abc/`. It is untracked in
   git but installed on the demonstration site. A bundle built from the working
   tree would ship it. **Remove it before the final commit and the bundle
   build.** It is not counted in the product's 144 entities.
3. **The scheduler is disabled on the demonstration site.** Scheduled
   behaviour was observed on the Rocky Linux 9 rehearsal host, where the kit
   enables it (every Consilium job ran exactly once), and in tests.
4. **Formation approval does not check approval evidence.**
   `charters.clearance_blockers` includes "no approval evidence is recorded",
   but `formation.approval_blockers` calls only `uncleared_challenges`.
5. **Demonstration disbandment FDIS-2026-00001 predates the three-approver
   rule.** It was executed with two approvals, and neither demonstration plan
   has a plan file attached.
6. **Doc AI and horizon scanning are switched on with no address on the
   demonstration site.** So their buttons show the "not connected yet"
   explanation, which is the intended state until an administrator enters the
   organisation's addresses in Admin → Integrations. The AI endpoint, by
   contrast, is connected (O-6).
7. **Time To First Action** is measured in `sla.py` and tested, but no SLA
   Definition on the demonstration site uses it, and no page shows it.
8. **`/policy-impact`** exists but no page links to it; the same panel is
   embedded on `/policy`.
9. **A stale docstring.** The one in `policy/handling.py` still says its
   `hooks.py` entries are not registered. They are.
