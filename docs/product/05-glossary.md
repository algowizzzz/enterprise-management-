# Consilium — Glossary

**Document:** 05 of 07 — Glossary
**Scope:** every domain term, abbreviation, role and platform term used across documents 01–07.

Terms are industry-standard. Where the source corpus used an abbreviation
without defining it, the expansion is given and the source of the expansion is

## A. Governance and risk domain terms

| Term | Definition |
|---|---|
| **Accountable Executive** | The executive answerable for an escalation matter and for the adequacy of its resolution. Named on the escalation, the action plan and the risk acceptance. |
| **Addendum** | A governing document that modifies or supplements another without replacing it. One of the three relationship types in document lineage. |
| **Applicability** | The set of business units, subsidiaries, material entities, jurisdictions and roles to which a governing document applies. Distinct from ownership: a document owned by one organisation may apply across many. |
| **Approval evidence** | Proof that an approval was given, in a form the governance standard accepts: email, meeting minutes, a signed document, or an in-system approval. |
| **Attestation** | A periodic, positive confirmation by a named accountable person that a stated set of facts is accurate. Three distinct attestation events exist in this platform (see §D). |
| **Cadence** | The scheduled meeting frequency of a governance forum. |
| **Casting vote** | An additional vote the chair may exercise to break a tie, where the forum's rules permit it. |
| **Charter** | The document establishing a governance forum: its mandate, scope, membership, decision rights and reporting lines. Also called a mandate. |
| **Committee** | A governance forum with formal decision rights. In this platform, one value of the forum-type taxonomy alongside council, oversight body and working group. |
| **Compliance status** | The forum's standing following compliance review: Draft, Pending, Compliant, Non-Compliant or Not Applicable. In this platform it *is* the forum's workflow state, not a separate attribute. |
| **Council** | A governance forum that coordinates and advises, typically without independent decision rights. |
| **Delegating authority** | The body or person whose authority a forum exercises. A forum cannot be stood up without one, and disbandment requires its approval. |
| **Delegation** | A time-bounded transfer of specified actions from an accountable person to another, recorded so that "who was acting for whom, when" is answerable. |
| **Disbandment** | The formal dissolution of a governance forum, requiring a plan, named approvals and a records disposition decision. |
| **Disposition** | The action taken on a record when its retention period expires: destroy, archive permanently, or review. Never automatic. |
| **Effective challenge** | Structured questioning of a first-line assessment by the second line of defence, before a matter proceeds. A control, not a courtesy. |
| **Escalation matrix** | The approved mapping from escalation attributes to severity and to the required pathway. The routing authority for escalation. |
| **Escalation matter** | A specific issue raised through the escalation process for decision at a defined authority level. |
| **Escalation pathway** | The route an escalation follows: the governance forums and authority levels that must consider it, in order. |
| **Escalation threshold** | The condition at which a matter must leave a forum and be escalated upward. |
| **Escalation trigger** | The event or condition that caused a matter to be escalated. |
| **Exemption / deviation** | A formal, approved and time-bounded release from a governing document's requirements for a named scope. |
| **Framework** (governing document type) | The highest tier of governing document, setting principles and structure below which policies sit. |
| **Governance forum** | Any standing body — committee, council, oversight body, working group — with a mandate, membership and reporting lines. The platform's umbrella term. |
| **Governing document** | The umbrella term for the five document types the platform manages: Framework, Policy, Standard, Procedure, Supporting Document. |
| **Governance responsibility** | What a forum is accountable for doing: oversight, or decision making, or both. |
| **Horizon scanning** | A periodic obligation on a document owner to identify emerging regulatory, technological, operational, environmental and geopolitical change that may require the document to be revised. In this platform it is a *record of a human activity*, not an automated feed. |
| **Impact sizing** | The structured assessment of what a governing document change will require across people, process, technology and data. |
| **Implementation** | The act, performed by the front line after publication, of putting a governing document into operational effect. A distinct lifecycle state, not a synonym for publication. |
| **Implementation verification** | The owner's subsequent confirmation that the processes, controls and governance structures the document required were actually put in place. Distinct from implementation itself. |
| **Intake** | The controlled request to create, change or retire a forum or a governing document. The entry point to every lifecycle in the platform. |
| **Jurisdiction** | The legal territory whose law applies: provincial, federal or international. |
| **Legal entity** | A distinct incorporated entity within the group. |
| **Legal hold** | A suspension of disposition, placed for litigation, investigation or regulatory reasons. Overrides retention unconditionally; does not alter the retention class. |
| **Line of business** | A second-level organisational division, below the operating group. |
| **Line of defence** | The three-lines model: the first line owns and manages risk; the second line oversees and challenges; the third line provides independent assurance. |
| **Major change / minor change** | The classification of a proposed change to a governing document. Major changes require full re-approval; minor changes follow a streamlined path. In this platform the classification is produced by a configurable rules engine, not by fixed logic. |
| **Mandate** | See *Charter*. Also used for the specific scope of authority a forum holds. |
| **Material entity** | A legal entity designated material for regulatory or resolution purposes, attracting additional governance obligations. |
| **Motion** | A proposition put to a governance forum for decision. The object a vote is cast on. |
| **Operating group** | The top level of the organisational hierarchy. |
| **Oversight body** | A governance forum whose role is supervision rather than execution or decision. |
| **Policy** (governing document type) | A governing document setting mandatory requirements within a framework. Also used loosely for the whole governing-document estate — this document set avoids that looser use. |
| **Policy family** | A parent governing document together with its children and addenda. |
| **Policy violation** | A recorded instance of non-conformance with a governing document. |
| **Primary risk category** | The single principal risk category a forum or governing document addresses. Singular by definition. |
| **Procedure** (governing document type) | A governing document setting out how a standard is carried out operationally. |
| **Quorum** | The minimum participation required for a forum's decisions to be valid. Expressed per forum as a count, a percentage, all voting members, or the chair plus a count. |
| **Regulatory required** | A flag indicating that a forum or governing document exists because a regulation requires it, obliging the capture of the specific regulatory detail. |
| **Retention class** | The rule set determining how long a record is kept, from what trigger, and what happens at the end. |
| **Retirement** | The formal end of a governing document's operative life. The retained record and its version history survive it. |
| **Risk acceptance** | A documented, approved and time-bounded decision to accept a risk rather than remediate it. Subject to periodic reassessment. |
| **Risk appetite breach** | An event where risk exceeds the stated appetite, triggering a defined escalation path. |
| **Risk management framework** | The enterprise structure of principles, taxonomy and governance within which risk is managed. Governing documents and forums are expected to align to it. |
| **Risk taxonomy** | The structured classification of risk types, here tiered: tier 1 and tier 2. |
| **Second line of defence** | The oversight and challenge function, independent of the first line that owns the risk. |
| **Sensitive escalation** | An escalation flagged for restricted visibility. The restriction must hold on every read path, not only on the record form. |
| **Service level** | An agreed time target for a workflow step, a status duration or total time open, with warning and breach thresholds. |
| **Standard** (governing document type) | A governing document setting specific mandatory requirements under a policy. |
| **Supporting document** | Guidance, templates and reference material accompanying a governing document without carrying independent requirements. |
| **Upstream / downstream forum** | The governance relationship between forums: a downstream forum reports or escalates to its upstream counterpart. |
| **Watched field** | A field whose modification triggers a compliance re-review. An admin-editable list, not a constant. |
| **WORM** | Write Once, Read Many. A storage property under which written data cannot be altered or deleted for its retention period. See §E for what it means concretely here. |

## C. Roles

Roles fall on two axes. The distinction is structural, not cosmetic: the access
axis is enforced by the permission engine, the accountability axis is recorded
on the individual record, and **both must hold** for an action to be valid.

### C.1 Access roles — what a person may do to a class of record

| Role | Scope |
|---|---|
| **Administrator** | Platform configuration: taxonomies, workflows, roles, notification templates, rules engine, watched fields, retention classes |
| **Viewer** | Read-only access within the permitted scope |
| **Reviewer** | May provide review input on records routed to them |
| **Approver** | May record an approval decision on records routed to them |
| **Committee Secretary** | Administers a forum: membership, meetings, minutes, agendas |
| **Forum Owner** | Accountable for a forum's accuracy and its annual attestation |
| **Policy Owner** | Accountable for a governing document through its lifecycle |
| **Enterprise Policy Office** | Central review, publication, glossary, monitoring oversight |
| **Risk Governance Office** | Formation evaluation, charter challenge, approval validation, inventory integrity |
| **Compliance** | Forum compliance review; policy conformance monitoring |
| **Legal** | Regulatory and legal review |
| **Audit** | Independent read access across the estate for assurance |
| **Escalator** | May raise an escalation matter |
| **Response Owner** | Accountable for delivering an escalation response |
| **Second Line of Defence** | Effective challenge on escalations and governing documents |
| **Front Line / First Line** | Raises intake requests, drafts, and confirms implementation |
| **Drafter** | Assigned to author a governing document draft |
| **Head of Risk Governance** | Resolves disputes and exceptions in the formation process |
| **Head of Enterprise Risk** | Terminal escalation point for systemic issues |

## D. Platform terms specific to Consilium

| Term | Meaning |
|---|---|
| **Consilium** | The working name of this platform. One product, three modules, shared Core. |
| **Core** | The shared layer: taxonomy, identity and delegation, attestation engine, classification rules engine, watched fields, version chain and revert, retention and WORM, import and export, notification, service levels, approval decisions, AI provenance. Built once. |
| **Module** | One of CGF, Policy, Escalation. Not a separate system, a separate deployment, or a separate database. |
| **Semantic flag** | A boolean on a workflow-bearing record — `is_editable`, `is_active`, `requires_review` — set by the workflow on transition. **All business logic reads these; none compares a workflow state string.** This is what makes a state rename configuration rather than a rebuild. |
| **The three attestation events** | (1) Annual first-quarter **forum inventory attestation** by chairs, secretaries and forum owners; (2) annual **governing document attestation** by document owners; (3) annual **forum owner and compliance review**, dually signed. Three events, one engine. |
| **Classification rule set** | The versioned, admin-defined set of questions, answer options and rules that produces a major/minor change classification. Data, not code. |
| **Classification assessment** | The immutable record of one evaluation: the answers given, the rule that fired, the outcome, and the full trace of every rule considered. |
| **Document version** | An immutable snapshot in a governing document's or charter's version chain: the body file, its hash, and the full field state at that version. **The authoritative record of what the document said.** |
| **Revert** | Restoring a prior version by **writing a new version** containing the old content. History is never rewritten, and the revert itself is an audited act. |
| **Watched field set** | The admin-editable list of fields whose modification triggers compliance re-review, with the action to take. |
| **Retention class / retention assignment** | The rule, and the binding of that rule to a population of records. |
| **Archive record** | The immutable, hash-chained retention artefact holding a record's fields, body, attachments and audit trail. |
| **Disposition event** | The scheduled, held, approved and executed end of a retention period. Outlives the record it disposed of. |
| **Import batch / import row / import profile** | The governed file-import pipeline that replaces the four connectors. The profile holds the mapping and handling rules; the batch holds the file, its hash and the validation report; the rows hold raw and mapped payloads. |
| **External reference** | A recorded, reportable foreign identifier with a known provenance batch, standing where a live connector would otherwise be. |
| **AI service request / AI suggestion acceptance** | The two provenance records around an AI call. The first answers "what data left the building"; the second answers "who took responsibility for machine-generated content, and against which version". |
| **Forum membership** | A standalone, dated seat record. Closed by setting an end date, never deleted, so the composition of a forum at any past date is a simple query. |
| **By-position seat** | A membership seat held by a titled position rather than a named person, so the seat survives the person leaving. |
| **Forum motion / forum vote** | A proposition put to a forum, and one row per entitled voter. Entitlement is recorded by creating the row, whether or not a vote is cast. |
| **Hybrid UI** | Custom vendored Bootstrap and jQuery screens for daily-use pages; native Desk for administration. One backend, one permission model, two presentation surfaces. |
| **Desk** | The framework's own administrative single-page application. Used for configuration, reporting and audit views. |
| **Vendored** | Shipped inside the repository and served from local assets. No content delivery network, no package-manager fetch. On an air-gapped server this is the only thing that works. |

## E. Technical terms used in documents 03 and 04

| Term | Meaning in this context |
|---|---|
| **Air-gapped** | No network path in or out of the secure zone. Everything is pre-staged and transferred on a reviewed one-way medium. |
| **Child table** | An entity whose rows are owned by a parent row, related by the parent's key plus the parent's entity name and the field it occupies. Its own physical table. |
| **DocType** | The framework's term for an entity definition. One DocType, one table. |
| **docstatus** | The draft / submitted / cancelled marker present on every table. 0, 1, 2. |
| **Dynamic link** | A polymorphic reference held as a pair of columns: the target entity name, and the target row's key. |
| **Link field** | A reference to exactly one row of another entity, stored as that row's key in a `varchar(140)` column. **There are no foreign keys in this schema.** |
| **MCP** | Model Context Protocol. The interface over which the external AI services platform is reached. |
| **Metadata-driven** | Entity definitions, workflows, permissions and reports are configuration records in the database, not code. Changing them is an administrative act. |
| **Naming series** | A key-generation strategy producing human-quotable identifiers with a counter, e.g. `FRM-2026-00042`. |
| **Partial index** | An index carrying a predicate, used here to enforce uniqueness that holds only for current or non-cancelled rows. |
| **Semantic versioning of rule sets** | Rule sets are versioned and never edited in place once used, so a past decision remains explicable against the rules live at the time. |
| **Submittable** | An entity whose records become read-only once submitted. Used for append-only audit artefacts, with cancel and amend revoked from every role. |
| **Table MultiSelect** | The framework's multi-valued reference construct: a child table whose rows each hold one link. |
| **Trigram index** | A PostgreSQL index type that makes leading-wildcard text matching indexable. |
| **Version log** | The framework's field-level change history. A **forward diff trail**, not a snapshot store — which is why the document version chain and revert are built rather than configured. |
| **Workflow action** | The framework's immutable record of who took which workflow action, when. |
| **WORM, concretely** | Four mechanisms together: no application path that updates or deletes; database privileges revoked from the application role; a hash chain making tampering detectable; and immutable storage for payload files. The fourth is an infrastructure decision that has not been taken — see `07-assumptions-and-gaps.md`. |
