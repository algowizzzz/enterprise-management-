# Consilium — Requirements Baseline

**Product:** Consilium, an enterprise Governance, Risk & Policy platform
**Document:** 01 of 07 — Requirements Baseline
**Status:** Baseline for build. Supersedes the source requirement documents where a stakeholder decision is recorded below.

---

## 1. Purpose and how to read this document

This is the single restatement of all 64 functional requirements carried by the
programme, sanitized of client-identifying material and reconciled against the
stakeholder decisions taken since the source documents were written.

Requirement identifiers are preserved exactly (`G-1..G-19`, `P-1..P-26`,
`E-1..E-19`) so that this document, the source corpus and the traceability
matrix in `06-traceability.md` line up one-to-one.

### Columns

| Column | Meaning |
|---|---|
| **ID** | Source requirement identifier. Never renumbered. |
| **Title** | Short name. Normalised where the source was inconsistent. |
| **Statement** | What the system must do, restated in neutral terms. |
| **Module** | `CGF` (Committee & Governance Forum), `POL` (Policy), `ESC` (Escalation), `CORE` where the capability is shared. |
| **Priority** | Source priority. All 64 are Mandatory. |
| **How satisfied** | `Native` / `Config` / `Build` / combinations — see §2. |
| **Δ** | Marked `Δ` where a stakeholder decision has **changed** the requirement from its source form. The change is described in §4. |

### Satisfaction classes

| Class | Definition |
|---|---|
| **Native** | Delivered by a stock framework feature with no schema or code work (version log, comment threads, permission engine, attachment handling, report builder, REST API). |
| **Config** | Delivered by declaring DocTypes, fields, workflows, permission rules, notification definitions, assignment rules or reports. Metadata, not code. |
| **Build** | Requires application code — server-side hooks, a service, an adapter, a custom screen, or business logic that cannot be expressed as configuration. |

Most requirements are a combination. The class shown is the **dominant** one;
the "how" text names the rest.

### Source priority — a note on record

Every one of the 64 requirements in the three source requirement documents
carries `Priority: Mandatory`. The only requirements anywhere in the corpus
marked `Optional` are seven items on the business-requirements deck, and a
stakeholder decision has since brought all seven into scope. They are listed in
**Appendix A** as `O-1..O-7`; they are supplementary to the 64, not a
replacement for any of them.

## 2. Scope frame — decisions that apply to every requirement

These eleven decisions are binding and change how many individual requirements
are read. They are stated once here rather than repeated 64 times.

| # | Decision | Effect on the requirement set |
|---|---|---|
| **S-1** | **One platform, three modules.** Committee & Governance Forum, Policy and Escalation are modules of a single product with a shared Core, not three integrating systems. | Every cross-module "integration" requirement (G-19 to Policy and Escalation; P-5 to governance forums; E-7 and E-19 to the forum inventory) collapses to an in-database relationship. Shared entities — users, taxonomies, attestation, audit, access control, retention — are built **once**. |
| **S-2** | **Connectors are out of scope.** The enterprise risk register, the risk appetite system, the GRC platform and the regulatory-change feed are all replaced by **manual and file-based import** in this phase. | The inbound/outbound integration halves of P-6, P-20, P-22, E-19 and G-19 become an **import path** (file upload, mapped, validated, staged, committed) plus an export path. The field mapping, validation and handling-rule requirements survive intact and apply to the import path. |
| **S-3** | **Retention and WORM are ours to build.** They are no longer an outbound hook to an external records system. | P-18, E-18 and G-16 change from "send to a retention system" to "implement retention classes, retention holds, immutable archival and disposition, in platform". This is a larger scope than the source implied. |
| **S-4** | **The document editor is external and independent.** Documents are uploaded manually. **This platform holds the authoritative document body and its version chain.** | P-26's collaborative editing, inline commenting and real-time disposition belong to the external editor. The version chain, retention of prior versions, and **revert** belong to us. |
| **S-5** | **Version revert is in scope.** | P-9, G-9 and E-12 gain a revert capability the source documents did not ask for. Revert is implemented as a forward-only operation: reconstruct the target snapshot, write it back as a **new** version, record the revert as an auditable act. History is never mutated. |
| **S-6** | **AI services are external, reached over an MCP interface.** | No AI model is built, hosted or trained here. Where a workflow offers an AI action, the platform records the request context sent and, if a user accepts a suggestion, the provenance of that acceptance against a specific record version. |
| **S-7** | **Identity is app-native with pluggable SSO.** | User records in the platform are the source of truth for every person-shaped link. LDAP and OIDC login methods are enabled later as authentication methods, not as a directory of record. |
| **S-8** | **Taxonomies are admin-maintained tables with CSV import.** | No external taxonomy synchronisation in this phase. The "aligned to enterprise taxonomies maintained by designated systems of record" clauses in G-19, P-20 and E-19 are satisfied by controlled, auditable, admin-maintained tables plus a documented import path. |
| **S-9** | **Classification rules are admin-configured.** | P-16's major/minor decision is a **rules engine** — admin-defined question sets, answer options and resulting classifications — not hard-coded logic. |
| **S-10** | **Watched fields are an admin-editable list.** | The "changes to certain fields trigger a compliance review" behaviour is a configurable field set, shipped with a default, editable in the UI. |
| **S-11** | **Hybrid UI.** Custom vendored Bootstrap + jQuery screens for the pages users see daily; native Desk for administration, taxonomy maintenance, workflow configuration, report building and audit. | Requirements about search, filtering, tables, dashboards and admin screens are satisfied on one surface or the other; `06-traceability.md` names which. Every table on a custom screen carries pagination, sort, search and configurable page size. No table plugin. Font-size control and a light/dark theme switch are present on every custom page. |

## 4. Where a stakeholder decision changed the requirement

Every row marked `Δ` above appears here. `**Δ**` (bold) marks a **material** change — the requirement's scope or delivery mechanism is different from what the source document described. Plain `Δ` marks a clarification or a narrowing that does not change the outcome.

| Requirement(s) | Source form | Decided form | Materiality |
|---|---|---|---|
| G-16, P-18, E-18 | "Send documents and data in a write-once form **to retention systems**" — an outbound hook to an external records platform. | **We own retention and immutability.** Retention classes, schedules, legal holds, immutable archival and disposition are built in this platform. | **Material.** This is the largest single scope increase against the source set. |
| G-19, P-20, P-5, P-6, P-22, E-19 | Live bidirectional connectors to the enterprise risk register, risk appetite system, GRC platform and regulatory-change feed. | **Connectors are out of scope.** Each becomes a **manual/file import** inbound and a **file export** outbound, with the same mapping, validation, handling-rule and traceability obligations applied to the import batch. | **Material.** Removes the largest unknown in the programme and replaces it with a design we control. |
| P-26, P-15 | A full collaborative editing capability with inline commenting, revision suggestion and real-time disposition, built here. | The **document editor is an external, independent application**; documents are uploaded manually. Ours: review-stage transition, reviewer assignment, disposition record and notification, the **authoritative document body and its version chain**, and retention of prior versions. | **Material.** Removes the largest single build item and adds the version-chain build. |
| P-9, G-9, E-12 | Track history; archive and view previous versions. | Plus **revert**: an authorised user may restore a prior version. Implemented forward-only — reconstruct, write as a new version, record the revert as an auditable act. History is never rewritten. | **Material.** Revert is not a framework feature. |
| P-16 | A dynamic question set determines major or minor classification; the decision rules are not stated anywhere in the source. | **An admin-configured rules engine.** Administrators define question sets, answer options, rules and resulting classification. The rules will change; they are data, not code. | **Material.** Converts the one blocked business-logic item into a configurable capability that can ship without the rules. |
| G-18 | The field list is **document-centric** (Document Name, Document ID, Document Type, Document Sponsor) on what is a committee intake form, and duplicates the policy metadata list almost exactly. | **Committee-centric naming** (Forum Name, Forum ID, Forum Type, Forum Sponsor), matching G-3's vocabulary. The document-centric list is treated as inherited from the policy template. | **Material** to the field names; immaterial to the shape of the record. |
| G-5, G-6, G-17 + slide-level compliance flow | Two incompatible state machines described for the same object. | **Two records, two workflows.** The multi-state formation/approval flow belongs on `Committee Formation Request`. The simpler compliance flow — Draft → Pending → Compliant / Non-Compliant / Not-Applicable — belongs on `Governance Forum`. An approved request **creates** a forum in Draft. | Resolves an apparent conflict without discarding either source. |
| G-3 | Primary risk category, legal entity and owning organisation read as single values. | **Business units, risk types, legal entities and jurisdiction are multi-select.** Two carve-outs stay single because the requirement itself is singular: **primary** risk category, and owning organisation. | **Material** to the physical schema — see `03-schema.md` §6. |
| G-10, P-8 | G-10 requires an annual first-quarter forum inventory attestation. P-8 separately requires annual policy attestation. A third annual review by forum owner and compliance appears on the deck. | **Three distinct attestation events, one shared engine.** Three campaign types over one campaign/task model. | Clarification. Prevents three parallel builds. |
| G-13 | "voting vs. non-voting" appears only as a user-grouping example. | **Votes are recorded**: who was entitled to vote, who voted, how, the outcome, and whether quorum was met. | **Material.** Adds motion and vote entities that no source document specifies. |
| G-13, P-13, E-16 | Three different and partly overlapping role vocabularies across the corpus. | **All three are modelled**, on two axes: *access* roles become platform roles; *accountability* roles become fields or rows on the record they apply to. | Clarification. |
| G-2, P-2, E-2 | "Advanced search and filter." | Satisfied twice: native list/report filtering on administrative screens, and a **hand-built** filter/sort/search/paginate control with configurable page size on every custom screen. No table plugin, no content delivery network. | Clarification with a real build cost. |
| G-14, P-14, E-17 | Configurable templated notifications, email and in-application. | Plus a **pluggable channel abstraction** so an enterprise chat channel can be added later without touching the notification definitions. | Clarification. |
| G-6 | "Administratively configurable without custom development." | Reaffirmed, with a standing engineering rule: **never key business logic off a literal workflow-state string.** Logic keys off semantic flags the workflow sets (`is_editable`, `is_active`, `requires_review`). A state rename or an added approval step is then configuration, not a rebuild. | Engineering constraint derived from the requirement. |
| P-1, P-3 | The governing-document type taxonomy. | The legacy type **"Directive" is not modelled.** The taxonomy is Framework, Policy, Standard, Procedure, Supporting Document. | Narrowing. |
| E-7, E-8, E-14 | E-7 reads as a single escalation pathway; the template appendix says **governance forum(s)** and **impacted entities**, plural. | **Plural wins** — both are child tables. The escalation date and the identification date are separate fields, as the template appendix states. | **Material** to the schema; the appendix is the more authoritative source. |
| E-13, P-7 | Service-level tracking named as a capability. | Explicitly a **build**: a service-level definition entity, a clock that accrues per state, and breach detection. The framework does not ship this. | Clarification with a real build cost. |
| E-16, P-1, P-13 | Restricted or sensitive records limited to authorized users. | Explicitly a **build**, because the restriction must hold on every read path — list, form, report, search, export and the platform's own interface — not only on the form. | Clarification with a real build cost. |
| P-1, P-13 | "Limit view, download, print and share." | The framework has no native print/download/share suppression per record. This is a **build**. | Clarification with a real build cost. |
| All 64 | Three separately scoped systems. | **One platform, three modules, shared Core.** Shared entities built once. | **Material** to build sequencing and to what "done" means. |
