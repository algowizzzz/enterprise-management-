## 1. Table naming

### 1.1 The rule

Every entity becomes exactly one table named `tab` + the entity name, **spaces
and capitals preserved**.

| Entity | Table |
|---|---|
| `Governance Forum` | `"tabGovernance Forum"` |
| `Forum Membership` | `"tabForum Membership"` |
| `Document Version` | `"tabDocument Version"` |
| `Escalation Matrix Rule` | `"tabEscalation Matrix Rule"` |

The framework writes DDL with backtick identifiers and the PostgreSQL driver
rewrites every backtick to a double quote before execution
(`modify_query`, `frappe/database/postgres/database.py`). The consequence for
anyone writing SQL by hand or pointing a reporting tool at this database:

> **Every identifier is mixed-case and contains spaces, so every identifier must
> be double-quoted in every statement.** `SELECT * FROM tabGovernance Forum` is a
> syntax error. `SELECT * FROM "tabGovernance Forum"` is correct.

### 1.2 Schema placement

All tables are created in the connection's default schema, which is `public`
unless `db_schema` is set in site configuration. The framework reads that
setting when listing tables but does **not** set `search_path` on the connection
and does **not** schema-qualify DDL. Verified in
`frappe/database/postgres/database.py`.

**Recommendation:** leave the platform in `public` and give reporting consumers
a separate read-only role with `USAGE` on `public` and `SELECT` on the tables
they need. Introducing a non-default schema means managing `search_path` per
role, and the framework will not help.

### 1.3 Reserved internal tables

Not entity tables. Created directly by the framework.

| Table | Purpose | Definition |
|---|---|---|
| `"__Auth"` | Password and secret storage, keyed `(doctype, name, fieldname)`. | `doctype varchar(140) not null, name varchar(255) not null, fieldname varchar(140) not null, password text not null, encrypted int not null default 0, primary key (doctype, name, fieldname)` |
| `"__global_search"` | The website search index. | `doctype varchar(100), name varchar(140), title varchar(140), content text, route varchar(140), published int not null default 0, unique (doctype, name)` |
| `"__UserSettings"` | Per-user list view state. | `"user" varchar(180) not null, doctype varchar(180) not null, data text, unique ("user", doctype)` |
| `"tabSeries"` | Naming-series counters. One row per series prefix. | Created from the framework's bootstrap SQL. |

> **`tabSeries` is a hot row.** Every record created under a naming series takes
> a row lock on its prefix. In a bulk import this serialises. See §7.4.

## 2. The columns every table carries

### 2.1 Standard columns — parent tables

Generated by `PostgresTable.create()`. These are not fields we declare; they
exist on every table without exception.

```sql
CREATE TABLE "tabGovernance Forum" (
    "name"        varchar(140) PRIMARY KEY,
    "creation"    timestamp(6),
    "modified"    timestamp(6),
    "modified_by" varchar(140),
    "owner"       varchar(140),
    "docstatus"   smallint     NOT NULL DEFAULT '0',
    "idx"         bigint       NOT NULL DEFAULT '0',
    -- declared fields follow
);
```

| Column | Type | Nullable | Meaning |
|---|---|---|---|
| `name` | `varchar(140)` | no (PK) | The row's identity and the value every reference to it stores. |
| `creation` | `timestamp(6)` | yes | Insert time. Note: **`timestamp without time zone`.** |
| `modified` | `timestamp(6)` | yes | Last update time. Used for optimistic concurrency. |
| `modified_by` | `varchar(140)` | yes | The user's `name`, i.e. their email address. |
| `owner` | `varchar(140)` | yes | Creating user's email address. |
| `docstatus` | `smallint` | no, default 0 | 0 draft, 1 submitted, 2 cancelled. |
| `idx` | `bigint` | no, default 0 | Ordinal within a parent. Meaningless on parent tables; present anyway. |

**Timezone.** `timestamp(6)` is *without time zone*. The framework stores times
already converted to the site's configured timezone. Any reporting consumer that
assumes UTC will be wrong by the site offset. This is not configurable per
table.

### 2.2 Optional columns — parent tables only

Four further columns are added to every non-child table
(`OPTIONAL_COLUMNS`, `frappe/database/database.py`), all `text`:

| Column | Contents |
|---|---|
| `_user_tags` | Comma-joined tag labels. |
| `_comments` | A JSON array cache of recent comments. |
| `_assign` | A JSON array of assigned users. **This is what the personal task list filters on.** |
| `_liked_by` | JSON array. |

A fifth, `_seen` (`text`), appears only where the entity sets `track_seen`.

> These are denormalised caches. They are **not** the system of record — the
> authoritative rows live in `"tabComment"`, `"tabToDo"` and `"tabTag Link"`.
> Never write to them directly and never treat them as authoritative in a report.

### 2.3 Child-table columns

A child entity's table carries the same seven standard columns **plus three**:

```sql
CREATE TABLE "tabForum Regulatory Requirement" (
    "name"        varchar(140) PRIMARY KEY,
    "creation"    timestamp(6),
    "modified"    timestamp(6),
    "modified_by" varchar(140),
    "owner"       varchar(140),
    "docstatus"   smallint NOT NULL DEFAULT '0',
    "idx"         bigint   NOT NULL DEFAULT '0',
    -- declared fields --
    "parent"      varchar(140),
    "parentfield" varchar(140),
    "parenttype"  varchar(140)
);
```

| Column | Meaning |
|---|---|
| `parent` | The **`name`** of the owning row. A string, not an integer. |
| `parenttype` | The owning entity's name, e.g. `Governance Forum`. Needed because one child table can be reused by several parents. |
| `parentfield` | Which field on the parent this row belongs to. Needed because one parent can hold two tables of the same child type — e.g. `upstream_links` and `downstream_links` both hold `Forum Link` rows. |

Child rows are **not** given the four optional columns. They cannot be tagged,
commented on, assigned or liked.

**A child row's full identity is therefore the triple
`(parent, parenttype, parentfield)` plus `idx` for ordering** — `name` alone is
unique but carries no meaning.

> ### 2.3.1 Divergence from MariaDB — verified, and it matters
>
> The MariaDB table builder adds two indexes that the PostgreSQL builder does
> not:
>
> | Index | MariaDB (`mariadb/schema.py`) | PostgreSQL (`postgres/schema.py`) |
> |---|---|---|
> | `parent` on every child table | `index parent(parent)` in the `CREATE TABLE` | **absent** |
> | `modified` on every parent table | `index modified(modified)` in the `CREATE TABLE` | **absent** |
>
> On PostgreSQL, the PostgreSQL builder creates indexes **only** for columns
> whose field metadata sets `search_index`, and only for non-text types.
>
> **Consequence:** without action, loading a forum with ten child tables
> performs ten sequential scans, and every list view sorted by `modified` — the
> default sort — performs a sequential scan and a sort. This is the single most
> important physical-schema action item in this document. See §7.1.

## 3. Type mapping

Verified against `setup_type_map()` in `frappe/database/postgres/database.py`.
`VARCHAR_LEN` is `140` (`frappe/database/database.py`).

| Logical type (doc 02) | Framework field type | PostgreSQL column type |
|---|---|---|
| `Data` | `Data` | `varchar(140)` |
| `Select` | `Select` | `varchar(140)` |
| `Link → X` | `Link` | `varchar(140)` |
| Polymorphic reference | `Dynamic Link` | `varchar(140)` |
| Read-only display | `Read Only` | `varchar(140)` |
| Phone, Colour, Icon, Autocomplete | — | `varchar(140)` |
| `Text` / `Small Text` / `Long Text` | `Text` / `Small Text` / `Long Text` | `text` |
| `Rich Text` | `Text Editor` / `HTML Editor` / `Markdown Editor` | `text` |
| Code | `Code` | `text` |
| `Attach` | `Attach` / `Attach Image` | `text` |
| `Check` | `Check` | `smallint NOT NULL DEFAULT 0` |
| `Int` | `Int` | `bigint` |
| `Int` with declared length > 11 | `Int` → promoted | `bigint` |
| `Decimal` (money) | `Currency` | `decimal(21,9)` |
| `Decimal` (general) | `Float` / `Percent` | `decimal(21,9)` |
| Duration in seconds | `Duration` | `decimal(21,9)` |
| Rating | `Rating` | `decimal(3,2)` |
| `Date` | `Date` | `date` |
| `Datetime` | `Datetime` | `timestamp` *(without time zone)* |
| Time of day | `Time` | `time(6)` |
| `JSON` | `JSON` | `json` |
| Secret | `Password` | `text` — **but the value is stored in `"__Auth"`, not in this column** |
| Barcode, Geolocation, Signature | — | `text` |

### 3.1 Consequences worth stating plainly

1. **There is no boolean type.** `Check` is `smallint NOT NULL DEFAULT 0`. Write
   `WHERE "confidential" = 1`, not `WHERE "confidential" IS TRUE`. Any
   reporting tool that maps a column to a boolean will need an explicit cast.
2. **There is no `timestamptz`.** See §2.1.
3. **`json`, not `jsonb`.** The framework maps `JSON` to `json`, which is stored
   as text, is not indexable with a GIN operator class without a cast, and does
   not deduplicate keys. Every `JSON` field in `02-data-model.md` —
   `population_filter`, `condition`, `evaluation_trace`, `validation_report`,
   `manifest`, `raw_payload`, `mapped_payload` — lands as `json`. **If any of
   these needs to be queried rather than merely stored, add a generated `jsonb`
   column and index that.** Do not attempt to change the framework's mapping.
4. **`decimal(21,9)` is the only numeric scale available** for `Currency`,
   `Float` and `Percent` without per-field precision metadata. A percentage
   stored here occupies nine decimal places.
5. **Text has no length limit and no index by default.** Long Text columns are
   excluded from the framework's automatic index creation (both builders skip
   `text` types).
6. **Declaring a field required does *not* produce `NOT NULL`.** Verified in
   `get_definition()`, `frappe/database/schema.py`: `NOT NULL` is emitted only
   for `Check`, `Int`, `Currency`, `Float` and `Percent`, and always with a
   default. Every other column — including every field doc 02 marks "Required:
   yes" — is nullable at the database level and mandatory only in the
   application. See §9.

## 4. How references are stored

### 4.1 A Link is a string

```sql
"primary_risk_category" varchar(140)
```

The column holds the **`name`** of the target row. There is no integer surrogate
key, no foreign key constraint, and no `ON DELETE` behaviour. Referential
integrity is enforced entirely in the application layer, on save and on delete.

**What this means in practice:**

| Question | Answer |
|---|---|
| Can a Link column hold a value that no longer exists? | Yes — if a row is deleted outside the application, or by a direct SQL statement, or by a framework path that skips the link check. |
| Will a join be fast? | Only with an index on the referencing column. The referenced side is the primary key, which is indexed. |
| Can two entities share a Link column name meaning different things? | Yes, and they will. `subject_name` on ten entities points at ten different tables, discriminated by `subject_doctype`. |
| Is cascade delete available? | No. Deleting a parent row deletes its child rows through application logic only. |

### 4.2 Dynamic Link — polymorphic references

Used throughout doc 02 for `subject_doctype` / `subject_name` pairs on
`Attestation Task`, `Document Version`, `Archive Record`, `AI Service Request`,
`Approval Decision`, `Metadata Remediation Task` and others.

```sql
"subject_doctype" varchar(140),   -- the entity name, e.g. 'Governing Document'
"subject_name"    varchar(140)    -- the row's name in that entity's table
```

There is no way to express this in a foreign key and no way to index it usefully
as a single unit. **Always index the pair, in that order** — see §7.2.

### 4.3 References to people

`User.name` is the person's **email address**, set in `User.autoname()`
(verified, `frappe/core/doctype/user/user.py`). Therefore every column in this
model typed `Link → User` — `committee_chair`, `document_owner`,
`accountable_executive`, `assigned_to`, `reverted_by`, and roughly eighty
others — stores an email address as a `varchar(140)`.

> **The consequence must be understood before go-live.** Changing a person's
> email address means renaming a primary key, which the framework supports
> through a rename operation that rewrites every referencing column it knows
> about. It is not a data update; it is a schema-wide operation, and it will
> miss any reference the framework does not know about — including anything
> stored inside a `json` column or a free-text field. Plan for it: name changes
> at marriage, domain migrations and legal-entity rebrands all trigger it.

### 4.4 Multi-valued references

A `Multi → X` field in doc 02 is a child table with a single Link column.
`forum.risk_types` becomes:

```sql
CREATE TABLE "tabForum Risk Type" (
    "name"        varchar(140) PRIMARY KEY,
    "creation"    timestamp(6),
    "modified"    timestamp(6),
    "modified_by" varchar(140),
    "owner"       varchar(140),
    "docstatus"   smallint NOT NULL DEFAULT '0',
    "idx"         bigint   NOT NULL DEFAULT '0',
    "risk_type"   varchar(140),      -- Link → Risk Type
    "parent"      varchar(140),      -- Link → Governance Forum (by name)
    "parentfield" varchar(140),      -- always 'risk_types'
    "parenttype"  varchar(140)       -- always 'Governance Forum'
);
```

Five such tables exist for `Governance Forum` alone (business units, risk types,
legal entities, jurisdictions, governance responsibilities), and more for
documents and escalations.

**Filtering a list by a multi-valued taxonomy is an `EXISTS` subquery, not a
column comparison:**

```sql
SELECT f."name", f."forum_name"
FROM "tabGovernance Forum" f
WHERE f."docstatus" < 2
  AND EXISTS (
      SELECT 1 FROM "tabForum Risk Type" rt
      WHERE rt."parent" = f."name"
        AND rt."parenttype" = 'Governance Forum'
        AND rt."parentfield" = 'risk_types'
        AND rt."risk_type" = 'OPERATIONAL'
  );
```

This is the direct cost of the multi-select decision, and it is the reason §7.1
insists on the `parent` index.

## 5. Primary keys and naming

### 5.1 The four naming strategies

| Strategy | `name` column | When we use it | Entities |
|---|---|---|---|
| **Naming series** | `varchar(140)`, e.g. `FRM-2026-00042` | Records people quote in conversation and in audit reports. | `Governance Forum`, `Committee Formation Request`, `Committee Charter`, `Governing Document`, `Document Intake Request`, `Escalation Matter`, `Action Plan`, `Risk Acceptance`, `Policy Violation`, `Forum Meeting`, `Forum Motion`, `Import Batch`, `Archive Record` |
| **Field value** | `varchar(140)`, the field's content | Taxonomies and configuration, where the code *is* the identity. | All seventeen taxonomies, `Glossary Term`, `Retention Class`, `External System`, `Escalation Matrix`, `Escalation Template`, `Document Template`, `Classification Rule Set`, `SLA Definition`, `Notification Channel` |
| **Hash** | `varchar(140)`, a random string | High-volume rows nobody quotes. | Every child table, `Forum Vote`, `Import Row`, `Notification Dispatch`, `AI Service Request`, `SLA Clock`, `Attestation Task` |
| **Autoincrement** | **`bigint`**, from a PostgreSQL sequence | Not used in this model. | — |

> **Autoincrement changes the primary key's type**, and with it the type of
> every Link column that points at the entity. Verified in
> `PostgresTable.create()`: the sequence path replaces
> `name varchar(140) primary key` with `name bigint primary key`. Mixing the two
> strategies across entities that reference each other produces a type mismatch
> on join. We use one strategy family — string keys — throughout, deliberately.

### 5.2 Naming-series format and the length budget

A series like `FRM-.YYYY.-.#####` produces `FRM-2026-00042`. The counter lives
in `"tabSeries"`, one row per prefix, incremented under a row lock.

140 characters is generous for a series key and tight for a field-value key. A
taxonomy whose code is the full title of a regulatory requirement **will**
exceed it. For `Regulatory Requirement` and `Glossary Term` use a short code as
the key and hold the full text in a separate column.

### 5.3 Uniqueness

The primary key is the only uniqueness PostgreSQL enforces by default. Where
doc 02 states a uniqueness rule that is not the primary key — one active chair
per forum, one current version per subject, one `(campaign, participant,
record)` attestation task — see §9.2.

## 7. Indexes

### 7.1 The two the framework will not create — create them first

Verified divergence (§2.3.1). These are not optimisations; without them the
platform's default behaviour is a sequential scan.

```sql
-- (a) every child table: the join back to its parent
CREATE INDEX IF NOT EXISTS "ix_forum_regulatory_requirement__parent"
    ON "tabForum Regulatory Requirement" ("parent", "parenttype", "parentfield");
-- ... repeated for all 31 child tables in the model

-- (b) every parent table: the default list sort
CREATE INDEX IF NOT EXISTS "ix_governance_forum__modified"
    ON "tabGovernance Forum" ("modified" DESC);
-- ... repeated for all 72 standalone tables
```

The composite `(parent, parenttype, parentfield)` is preferred over MariaDB's
single-column `parent` index: a child table reused by two parent fields —
`Forum Link` under both `upstream_links` and `downstream_links` — needs all
three to be selective.

**These must be generated, not hand-written.** A migration step that enumerates
the model's tables and emits both index families is the only way this stays
correct as entities are added.

### 7.2 The index-name collision hazard — verified, and it will bite

The PostgreSQL builder creates indexes like this
(`PostgresTable.create_indexes()` and `alter()`):

```sql
CREATE INDEX IF NOT EXISTS "compliance_status" ON "tabGovernance Forum" ("compliance_status");
```

**The index name is the bare field name.** It is not prefixed with the table.

In MariaDB index names are scoped to their table, so this is safe. **In
PostgreSQL index names share a schema-wide namespace.** Two entities that both
declare a search index on a field called `status`, or `forum`, or
`subject_name` — and this model has many such fields — produce:

1. First entity: `CREATE INDEX IF NOT EXISTS "status" ON "tabEscalation Matter" ("status")` → created.
2. Second entity: `CREATE INDEX IF NOT EXISTS "status" ON "tabAttestation Task" ("status")` → **`IF NOT EXISTS` matches the existing name and the statement silently does nothing.** The second table gets no index, and no error is raised.

The framework's own `has_index()` check queries `pg_indexes` filtered by
`tablename` **and** `indexname`, so it correctly reports "no index on this
table" — and then the `CREATE` is swallowed anyway. The same applies to unique
indexes, created as `"unique_<fieldname>"`, and to the multi-column form,
`"<field1>_<field2>_index"`.

**Mitigations, in order of preference:**

| Option | What it costs |
|---|---|
| **Do not rely on `search_index` field metadata at all.** Declare no search indexes in entity definitions; create every index explicitly in a migration with a table-prefixed name (`ix_<table>__<columns>`). | Discipline. This is the recommendation. |
| Add a compatibility patch that prefixes generated index names with the table. | A framework patch to own and re-verify on upgrade. The deployment toolchain already has a patch mechanism designed for exactly this, and a patch here is a no-op on MariaDB. |
| Accept it and audit `pg_indexes` after every migration. | An ongoing manual check that will eventually be skipped. |

> **This is the single highest-value finding in this document** and it is not
> documented anywhere in the framework. It was found by reading the two schema
> builders side by side.

### 7.4 Search indexes

Two different search paths, both weak on PostgreSQL out of the box.

**Path 1 — the in-form and link-field lookup.** `frappe/desk/search.py` builds
`WHERE <field> LIKE '%text%'`. A leading wildcard cannot use a B-tree index.

**Path 2 — website global search.** `frappe/utils/global_search.py` issues, on
PostgreSQL:

```sql
SELECT ... FROM "__global_search"
WHERE "published" = 1
  AND TO_TSVECTOR("content") @@ PLAINTO_TSQUERY('search text')
```

`to_tsvector` is computed **at query time, per row**, and there is no index on
`__global_search` beyond its `(doctype, name)` unique constraint. This is a
sequential scan plus a per-row tsvector build. On MariaDB the same table carries
a full-text index; on PostgreSQL it does not.

**Recommended remediation.** We hold superuser on this PostgreSQL instance, so
extensions are available:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

-- Path 1: make leading-wildcard LIKE indexable on the columns people search
CREATE INDEX IF NOT EXISTS "ix_governing_document__name_trgm"
    ON "tabGoverning Document" USING gin ("document_name" gin_trgm_ops);
CREATE INDEX IF NOT EXISTS "ix_governance_forum__name_trgm"
    ON "tabGovernance Forum" USING gin ("forum_name" gin_trgm_ops);
CREATE INDEX IF NOT EXISTS "ix_escalation_matter__title_trgm"
    ON "tabEscalation Matter" USING gin ("escalation_title" gin_trgm_ops);

-- Path 2: index the expression the framework actually evaluates
CREATE INDEX IF NOT EXISTS "ix_global_search__content_fts"
    ON "__global_search" USING gin (TO_TSVECTOR("content"));
```

> **Caveat on the second one.** `TO_TSVECTOR(text)` with one argument uses
> `default_text_search_config`, which is a *session* setting. An expression
> index on a one-argument `to_tsvector` call is **not immutable** and PostgreSQL
> will reject it. The index must be built on the two-argument form,
> `TO_TSVECTOR('english', "content")`, and the framework's query uses the
> one-argument form, so the planner will not match them. **Making global search
> fast therefore requires either patching the query to the two-argument form or
> setting `default_text_search_config` at the database level and accepting that
> the index cannot be created as written.** This is stated as a limitation, not
> a solved problem — it needs a decision. See `07-assumptions-and-gaps.md`.

**The pragmatic position for phase one:** the custom Bootstrap register screens
do their own filtered queries against indexed columns and do not use either
path. Global search is a secondary surface. Fix path 1 with trigram indexes;
treat path 2 as a known limitation.

### 7.5 Indexes to avoid

- **Do not index `text` columns with a B-tree.** The framework already refuses
  to (both builders skip `text` and `longtext`), and a B-tree over unbounded
  text will fail on rows exceeding the page limit.
- **Do not index low-cardinality `Check` columns alone.** `is_active` alone is
  useless; `(is_active, modified)` may not be.
- **Do not index `docstatus`.** It has three values and every query filters on
  it, so it belongs as the *trailing* column of a composite or in a partial
  index predicate, never alone.

## 8. Draft, submitted and cancelled

### 8.1 The mechanism

`docstatus smallint NOT NULL DEFAULT 0` (verified,
`frappe/model/docstatus.py`):

| Value | State | Framework behaviour |
|---|---|---|
| `0` | **Draft** | Freely editable, deletable. |
| `1` | **Submitted** | Every field becomes read-only unless explicitly marked editable-after-submit. Deletion is blocked. |
| `2` | **Cancelled** | The row remains. It is excluded from list views by default and from link-field validity. |

Amendment of a cancelled row creates a **new row** carrying `amended_from`
pointing at the cancelled one. A cancelled row is never reused.

### 8.2 The trap

> **Cancellation is not deletion, but it is also not immutability.** A user with
> the `cancel` permission on an entity can cancel a submitted record, and then
> amend it into a new one. For an append-only audit artefact this is precisely
> the wrong affordance.

### 8.3 What we submit, and what we do not

**Submittable** — the record is an assertion that must not change after it is
made:

| Entity | Why |
|---|---|
| `Document Version` | The version chain is append-only. Doc 02 §5.4. |
| `Classification Assessment` | P-16's audit trail of the classification applied. |
| `Approval Decision` | P-25's non-repudiable approval record. |
| `Forum Vote` | A cast vote. |
| `Forum Motion` | Once the outcome is recorded. |
| `Archive Record` | The retention artefact. |
| `Version Revert Log` | The record of a revert. |
| `AI Suggestion Acceptance` | Who took responsibility for machine-generated content. |

**For every one of these, the `cancel` and `amend` permissions are removed from
every role including Administrator.** Submittable gives us the read-only
enforcement; removing cancel and amend removes the escape hatch. This is a
permission configuration, and it must be asserted by a test, because a
permission left open is invisible until an auditor finds it.

**Not submittable** — everything else. The lifecycle of a forum, a document or
an escalation is expressed by its **workflow state and semantic flags**, not by
`docstatus`. Mixing the two produces records that are simultaneously "Published"
and "Draft", which is exactly the confusion the corpus already contains.

### 8.4 The query rule

**Every** query written by hand, every report and every external consumer must
filter cancelled rows:

```sql
WHERE "docstatus" < 2
```

The framework's own query layer does this. Direct SQL does not. A dashboard that
omits it will count cancelled records, and nobody will notice until a number is
challenged.

## 9. What the database enforces, and what it does not

This section exists because the honest answer surprises people.

### 9.1 What PostgreSQL enforces

| Constraint | Present? | Detail |
|---|---|---|
| Primary key on `name` | **Yes** | The only structural guarantee on every table. |
| `NOT NULL` | **Partially** | On `docstatus` and `idx` always; on `Check`, `Int`, `Currency`, `Float` and `Percent` columns, always with a default. **Nowhere else.** |
| Column type and length | **Yes** | `varchar(140)` will reject a longer value. |
| Unique constraint | **Only where explicitly declared** | Created as a unique index, either inline in the column definition or as `"unique_<fieldname>"`. Subject to the naming hazard in §7.2. |

### 9.2 What PostgreSQL does **not** enforce

| Rule | Enforced where | Risk if bypassed |
|---|---|---|
| **Referential integrity on every Link column** | Application only. There are **no foreign keys in this schema at all.** | A direct `DELETE` on a taxonomy row orphans every record referencing it. Silently. |
| **Required fields** | Application only. Declaring a field required produces no `NOT NULL` (verified, §3.1 point 6). | A bulk insert that skips the application layer produces records missing mandatory data, and every downstream report treats the null as a legitimate value. |
| **Child rows belong to a live parent** | Application only. | Orphaned child rows survive a parent deletion that bypassed the framework. |
| **One active chair per forum** | Application validation on `Forum Membership`. | Two chairs; quorum logic that reads `is_voting_chair` produces two casting votes. |
| **Exactly one `is_current` version per subject** | Application validation on `Document Version`. | Two "current" versions; the document body shown depends on sort order. |
| **`end_date >= start_date`** | Application validation. | A membership that was never valid still appears in an as-at query. |
| **Uniqueness of `(campaign, participant, record)` attestation tasks** | Application validation. | Duplicate attestation tasks; a campaign that can never report complete. |
| **An `Archive Record` is never updated or deleted** | Application convention plus permission configuration plus the hash chain. **Not a database guarantee.** | Undetected tampering, unless the chain is verified. |
| **Cross-field conditional requirements** (`regulatory_requirements` required when `regulatory_required = 1`) | Application only. | Regulatory-required forums with no regulatory detail. |

### 9.3 The recommended mitigations, and their cost

Three of these can be closed at the database level **without fighting the
framework**, because the framework never issues the statements they would
block:

```sql
-- 1. Uniqueness the framework cannot express. Partial unique indexes.
CREATE UNIQUE INDEX IF NOT EXISTS "ux_document_version__current"
    ON "tabDocument Version" ("subject_doctype", "subject_name")
    WHERE "is_current" = 1 AND "docstatus" < 2;

CREATE UNIQUE INDEX IF NOT EXISTS "ux_attestation_task__unique"
    ON "tabAttestation Task" ("campaign", "assigned_to", "subject_doctype", "subject_name")
    WHERE "docstatus" < 2;

CREATE UNIQUE INDEX IF NOT EXISTS "ux_document_version__number"
    ON "tabDocument Version" ("subject_doctype", "subject_name", "version_number")
    WHERE "docstatus" < 2;

-- 2. Cheap sanity checks the application also enforces.
ALTER TABLE "tabForum Membership"
    ADD CONSTRAINT "ck_forum_membership__dates"
    CHECK ("end_date" IS NULL OR "start_date" IS NULL OR "end_date" >= "start_date");

-- 3. Append-only enforcement on the archive, at the database.
REVOKE UPDATE, DELETE ON "tabArchive Record" FROM <application_role>;
```

**The cost and the caveats, stated plainly:**

- A `CHECK` constraint the framework does not know about will surface as a raw
  database error rather than a friendly validation message. Add the application
  validation **as well**, and treat the constraint as the backstop.
- Revoking `UPDATE` on `"tabArchive Record"` from the application role means the
  application can never touch those rows again — including for a legitimate
  schema migration. The migration must run as a different role. **This is a
  deliberate operational constraint and it needs to be written into the runbook,
  not discovered during an upgrade.**
- **Do not add foreign keys.** The framework deletes and renames rows in an
  order that does not respect them, and migration will fail in ways that are
  hard to diagnose. Referential integrity stays in the application. This is a
  known and accepted property of the platform, and a reviewer should be told so
  rather than left to discover it.
- Any constraint added here must be re-applied after a schema migration, because
  the framework's `ALTER` path does not preserve objects it did not create.
  **Constraint re-application belongs in the deployment script.**

## 10. File storage

Attachments are not stored in the database. `File` rows hold a path; the bytes
live on the filesystem under the site directory:

| Path | Visibility | Use |
|---|---|---|
| `sites/<site>/public/files/` | Served without authentication | Nothing in this platform. |
| `sites/<site>/private/files/` | Served only after a permission check | **Everything.** Charters, policy bodies, evidence, disbandment plans, import files, archive payloads. |

**Rules for this build:**

1. **Every attachment is private.** There is no governance artefact in this
   model that may be served unauthenticated.
2. `Document Version.body_file` and `Archive Record.payload_file` hold
   `/private/files/...` paths. The `body_sha256` and `payload_sha256` columns
   exist because the filesystem is outside the database's transactional
   guarantee — a file can be replaced without the row changing.
3. The retention and disposition logic acts on **both** the row and the file.
   Disposing of an archive record without removing its payload leaves the data
   in place; removing the payload without the row leaves a dangling reference.
   The disposition routine must do both, in that order, and record what it did.
4. `File` rows carry a `content_hash` used for deduplication. Two identical
   uploads may therefore share one stored file. **Disposition must not delete a
   file that another retained record still references.** This is a real
   correctness requirement, not a theoretical one.

## 11. Change history — what is stored and what it costs

Verified in `frappe/core/doctype/version/version.py` and
`frappe/model/document.py`.

A row is written to `"tabVersion"` on every save of an entity that enables
change tracking. Its `data` column is a JSON document:

```json
{
  "changed":     [["compliance_status", "Pending", "Compliant"]],
  "added":       [["risk_types", { ... full child row ... }]],
  "removed":     [["risk_types", { ... full child row ... }]],
  "row_changed": [["members", 0, "row-name", [["votes", 1, 0]]]]
}
```

Four properties matter for this build:

1. **It is a forward diff trail, not a snapshot store.** There is no "restore"
   operation. This is why `Document Version` exists in doc 02 §5.4 and why
   revert is a build.
2. **Child-table changes are captured**, as whole added and removed rows plus
   per-field row changes. So membership changes *are* in the version log — but
   reconstructing "who sat here in September" means replaying every diff in
   order, which is why membership is a standalone dated record instead.
3. **Large text fields are stored in full, twice.** The diff logic skips
   *formatting* for `Text Editor`, `Code`, `Markdown Editor` and `HTML Editor`
   fields but still records the old and new raw values. A rich-text field
   holding a policy body would write both copies into `"tabVersion"."data"` on
   every save. **This is a concrete reason not to hold document bodies in a
   `Text Editor` field** — they belong in `Document Version.body_file`, and
   `body_text` (a plain `Text` field) should be marked to skip change tracking.
4. **`"tabVersion"` grows without bound.** It has no retention of its own. A
   growth and archival policy for it is an operational requirement, and it
   interacts with retention: the version log is part of the audit trail that
   G-9, P-9 and E-12 require be retained.

## 12. Sizing and growth

Rough orders of magnitude, to inform index and partitioning decisions rather
than to predict storage. Assumptions are stated because they are assumptions.

| Table | Driver | Order of magnitude |
|---|---|---|
| `"tabGovernance Forum"` | Enterprise forum inventory | hundreds to low thousands |
| `"tabForum Membership"` | ~15 seats per forum, turning over annually, never deleted | tens of thousands, growing linearly with time |
| `"tabForum Vote"` | motions × entitled voters | tens of thousands per year |
| `"tabGoverning Document"` | Enterprise governing-document estate | low thousands |
| `"tabDocument Version"` | ~3–6 versions per document per year | tens of thousands |
| `"tabEscalation Matter"` | Escalation volume | thousands per year |
| `"tabAttestation Task"` | 3 campaigns × population × participants, annually | tens of thousands per year |
| `"tabVersion"` | **every save of every tracked entity** | **the largest table in the database, by an order of magnitude** |
| `"tabNotification Dispatch"` | every notification to every recipient | hundreds of thousands per year |
| `"tabImport Row"` | one row per line of every imported file | spiky; bounded by import volume |
| `"tabArchive Record"` | one per archived version | tracks `Document Version` |

**Actions this implies:**

- `"tabVersion"`, `"tabNotification Dispatch"` and `"tabImport Row"` need an
  archival strategy before they need partitioning. Decide it before go-live, not
  after.
- Nothing here justifies table partitioning at the volumes above. Say so
  explicitly, so that nobody builds it speculatively.
- `"tabForum Membership"` grows forever by design. That is the price of M-1 and
  it is the right price.
